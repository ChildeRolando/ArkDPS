# ArkDPS 官服 PC 只读适配可行性报告

评估日期 2026-11-21。目标是鹰角启动器国服 Windows x64 客户端，验收基线为 ArkDPS rc.8 的 MuMu 功能。**原生只读累计采集已实机验证可行**，覆盖伤害、非零治疗、稀音召唤伤害、倍速、暂停、关卡和胜利结算。Windows 的逐事件来源仍有缺口，现有证据支持接入累计统计，完整数值齐平仍取决于逐事件和产品验收。[MuMu 产品基线](v1-design.md) · [PC 实验记录](native-pc-research.md)

### CE-5 治疗、倍速与胜利结算

实机候选 `355a70c` 从管理员 PowerShell 开始读，构建与模块字节校验通过。关卡源 ID `Obt/Weekly/level_weekly_melee_5` 确认 CE-5。到胜利并返回空单例后，由玩家结束采样。日志 753 条，含 693 份不同的有效同帧样本，另有 53 次跨帧或对象链变化重试。

| 验证项 | 结果 |
| --- | --- |
| 1× 与 2× | 稳定标准速度区间内，9.391 秒墙钟推进 9.400 秒游戏时间，比例为 `1.0010`。稳定高速区间内，58.015 秒墙钟推进 116.033 秒游戏时间，比例为 `2.0001`。部署期间的慢动作区间保留在原始记录里。 |
| 暂停 | 确认暂停的 12.234 秒内，心跳仍在记录。逻辑帧保持 `1706`，游戏时间保持 `56.866612` 秒。 |
| 治疗字段读数 | 闪灵来源累计从 0 增至 `34213.63671875`，全局治疗从 0 增至 `10511.4501953125`。这证明两字段都能观察到非零治疗。当前样本未逐次核算满血、过量和脱手治疗。 |
| 编队与宿主 | 693 份样本均读到编队。具体已核对的两组为 `token_10057_svash2_eagle2→char_1045_svash2` 和 `token_10066_closur_ourbase→char_4228_closur`。两组宿主键、UID 与阵营一致。本轮没有取得非零召唤伤害，也未记录在场实体集合。 |
| 胜利结算 | 三份终局样本均为状态 `3`、结果 `1`，关卡时间冻结于第 `6613` 帧、`220.433123` 秒，累计保持一致，之后确认战斗单例为空。失败、放弃、同图重开与产品写入历史仍待实测。 |
| 逐事件 | 全部有效样本的详细记录器为空。本局没有用于精确过量、盾吸收、接敌和技能期统计的有序事件证据。 |

本轮原始采集与复核回执分别为 `runtime/native-pc/2026-11-21-battle/ce5-heal-20261121-121044.jsonl` 和 `ce5-heal-20261121-121044.verified.json`。原始文件 SHA-256 为 `af60b404f9f60fd79c5441e96dda4b69d069ee8217c2cd953c0f611ec8f11184`。

### 1-7 稀音召唤伤害归属

本机只读采样原生关卡为 `Obt/Main/level_main_01-07`，演习和使用稀音由玩家确认。272 份有效同帧样本都核对到了同阵营的摄影小车 `token_10010_folivo_car` 与稀音 `char_336_folivo`，宿主键和 UID `2147483736` 唯一匹配。

小车首次出现在累计表时为 477，此后观察到 16 次相邻样本间累计增加，最终为 8,109，均为物理伤害。使用同帧编队和累计回放现有 `BattleStatisticsAdapter`，稀音总伤为本体 `0` 加小车 `8109`，只生成一条稀音排行记录。原生全局伤害 `6204` 单独保留。采样以战斗中暂停结束，在场实体数、哪台小车命中及撤退再部署仍待动作日志与实体采样核对。

原始文件为 `runtime/native-pc/2026-11-21-battle/summon-20261121-123256.jsonl`，同目录的 `.verified.json` 保存回放结果。原始文件 SHA-256 为 `104601a5b1190249eff3d829c821cac4e3b805998bbdb64671c8c05a08920a0a`。

### 1-7 同图重开与操作见证

`restart-20261121-125443.jsonl` 在同一读取进程内记录两局 1-7，共 99 份有效样本。第一局全局累计从 `0` 增至 `1050`，随后战斗单例为空。第二局从第 `6` 帧和累计 `0` 开始，随后增至 `460`。两局分别记录了稀音的手动部署，操作序号各从 `0` 开始。在场集合和手动操作探针在 99 份样本均可用。第一局没有原生终局结果字段，本次证据支持同图重开隔离，主动放弃的结果标签仍待核对。原始文件与同名 `.verified.json` 在 `runtime/native-pc/2026-11-21-battle/`，原始 SHA-256 为 `212c367c005a9882b8ac9e2868db3fc838a550514d00fb9ec2912e567e2a1109`。

## MuMu 功能齐平矩阵

| 能力 | Windows 现状 | 达到齐平的证据 |
| --- | --- | --- |
| 分类总伤害、近 5 秒 DPS | 分类计数、逻辑帧、1×、2× 和暂停已通过实机对照。现有统计核心可复用近期窗口，须先完成来源归属和正常入口接入。 | 中途启动、退场后的同口径对账与产品近期窗口验证。跨帧或归属缺失时保持未知。 |
| 治疗累计、近 5 秒 HPS | CE-5 已观测闪灵与全局非零累计。两个字段的口径各自保留。 | 区分缺血、满血、持续回血与脱手治疗，按来源核对近期窗口。 |
| 召唤物与离场输出、全周期速率 | CE-5 核对两组召唤宿主。在 1-7 核对稀音小车正向伤害，并用现有统计核心回放验证只归并一次。 | 用实例身份核对召唤并发、撤退和再部署。全周期分母需要宿主本人在场区间。 |
| 敌情、首领、有效伤害、过量和减伤 | 敌人瞬时状态是可调查的读源。当前累计伤害无法区分目标、击杀、盾吸收或公式前后值。 | 每个敌人实例有稳定标识。首领输出与过量需逐次来源、目标、HP 前后、结算值和盾上下文对账。 |
| 有效护盾、接敌 DPS/HPS、技能期拆分 | 现有 Windows 只读来源未提供完整有序的逐次事件。可读的盾剩余量或技能状态只能支持进一步验证。 | 实际盾吸收量与施盾人，逐次伤害与治疗帧，技能起止及输出归属。丢失短时事件时应报告覆盖缺口。 |
| 战局生命周期、HUD、侧栏、历史和导出 | 独立采样器已验证 CE-5 胜利结算和同一进程内 1-7 重开隔离。WPF 展示与统计逻辑具备复用边界。 | 通过正常入口验证失败和放弃、一次归档、平台切换、历史来源标识及 MuMu 回归。 |

MuMu 的事件来源与精度见[事件采集约定](event-capture.md)和[统计核心](statistics-core.md)。Windows 的开源 ArkHelper 快照公开了逻辑帧、行累计及覆盖标记。其发布端使用进程内观测，目前机器上没有该发布端，独立只读接收器已通过合成数据验证。公开快照还缺少 ArkDPS 所需的逐笔结算契约。[ArkHelper 快照接口](https://github.com/zhengkanqin/ArkHelper/blob/v1.4.2/include/arkhelp/ipc.h)

对匹配构建的磁盘元数据与 `GameAssembly.dll` 做了只读核对。`BattleLogger.m_logs` 保留带游戏时间的手动部署、撤退和技能指令，可用于下一步核对人工操作。`charStats` 和 `skillTrigStats` 保存计数，`CharAdvancedStats.snapshots` 保存属性、天赋和技能配置，普通事件池保存回调集合。这些已定位字段缺少逐击伤害、自动技能起止和护盾实际吸收的事件记录。

## 接入边界

- 将通过实机验证的 Windows 构建配置和读取器放入 Python 采集层。以进程创建时间和战局身份约束缓存，构建不匹配时停止发布数值。权限需求限于原生读取器，WPF 与 MuMu 的普通入口可继续使用各自权限。
- 在一个逻辑帧里核对累计、编队与在场集合。归属经过宿主键和 UID 验证后进入现有统计适配器。原生全局计数单独保留用于对照。中途进入使用首个可靠累计作基线，近期速率只从该点后的增量计算。
- 复用现有 `CollectionSession`、战局切换、统计、HUD 和归档路径。历史与导出保留平台、构建和事件覆盖说明。发布候选需同时通过原生生命周期实测与 MuMu 回归。事件相关功能以完整性判断为准。[桌面运行时](desktop-runtime.md) · [累计适配器](snapshot-adapter.md)

## 实测安排

玩家操作和完整命令集中在[官服 PC 实机验收手册](native-pc-player-test-guide.md)。

1. **已完成的 CE-5 演习。** 验证非零治疗、1×、2×、暂停和胜利结算，详见上表。
2. **已完成的 1-7 稀音演习。** 验证摄影小车的累计伤害与宿主合并。后续分别读取手动操作日志和在场实体集合。动作日志按数据 UID 关联统计来源，在场实体用实例 UID 区分。共享来源累计只合计一次。[MuMu 既有作业](../acceptance/maa/README.md)
3. **盾吸收与过量对账。** 沿既有 OF-8 闪灵 S2 破盾方案核对实际吸收量，再用孤立的末击超出目标剩余 HP 的样本对账。验收依赖可验证的结算证据，画面和累计都保留各自覆盖边界。[盾破实测](capability-validation.md)

只有 PC 实机观测能改变矩阵里的验证状态。若普通只读来源最终只能提供累计和部分瞬时状态，PC 能实现相应统计，完整数值齐平仍取决于可支持的有序事件接口。
