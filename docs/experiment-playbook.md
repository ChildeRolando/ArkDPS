# 实机实验手册：MAA 作业、关卡路线与守门

2026-11-08。适用本机 MuMu 12 / Android 2.7.91 / MAA 6.21.4。本页记录一套可重复的研究流程，不是产品功能说明；能力结论仍以 [底层能力实测](capability-validation.md) 和 [补充实验](recovery-validation.md) 为准。

## 适用范围与三条硬规则

这套流程用于在不修改游戏数值的前提下，用固定部署顺序制造可观测的战斗样本：验证伤害、治疗、护盾、召唤归属、事件时序和断连恢复等机制。

1. **实验必须可重放**：同一份作业（JSON）在同一关卡给出同样的部署顺序；不靠临场截图和手操。
2. **实验不能因漏怪提前结束**：每个蓝门都要有守门干员，且守门输出不得混入被测对象。
3. **判定只用客户端逻辑帧和事件证据**：MAA 的等待秒数、任务完成消息和墙钟都不是游戏时间。

开工前逐项确认：

- [ ] 只有一个被测机制，对照和排除项已写明。
- [ ] 关卡路线已从原始数据核对，坐标已转换为 MAA `[列, 行]`。
- [ ] 每个蓝门都有守门位，守门输出会单独排除。
- [ ] 关卡详情页已打开，**代理指挥已关闭**。
- [ ] 作业 JSON 放入 `acceptance/maa/` 并登记。
- [ ] 事件探针/采集器在点开始行动前就绪。
- [ ] 暂停帧、成功判据和失败处理已写明。

## 1. 先把实验写成一句话

开工前写清四项，缺一项就不要开始：

| 项 | 例子 |
| --- | --- |
| 被测对象 | 闪灵 S2 对夜刀的数值盾吸收 |
| 对照/排除 | 山和歌蕾蒂娅只负责守门，输出不计入被测对象 |
| 触发条件 | 碎岩者攻击 750，足以打破 316.5 的盾 |
| 停止条件 | 第 2964 帧暂停；或第 N 次盾破事件后 |

只改变一个机制。不要在同一局同时验证召唤归属和护盾到期；同时观察多个对象时，至少保证它们的累计项互不重叠。

## 2. 选图

- 优先 **OF 系列**：在本机当前活动条件下不消耗理智，可以反复跑；编号越大敌人属性越高。用高强度图放大机制（OF-8 的碎岩者能打破数值盾），用低强度图隔离机制（OF-2 的水獭与猎犬）。
- 选图看四件事：路线是否清楚、蓝门数量、敌人能否按时到达被测位置、部署格朝向是否够用。
- 不用主线图消耗理智；不用代理指挥；不要在活动关卡的限时或特殊规则下外推结论。
- 关卡数据只是计划依据，实机行为优先。公开提取数据与实际版本不一致时，以实测为准。

## 3. 先查路线，再放干员

### 3.1 找关卡数据

1. 在 [Kengxxiao/ArknightsGameData](https://github.com/Kengxxiao/ArknightsGameData) 找到对应活动目录，例如 `zh_CN/gamedata/levels/activities/act3d0/level_act3d0_02.json`（OF-2）、`level_act3d0_08.json`（OF-8）。
2. 记录下载文件的 SHA-256 和日期。引用路线时同时写来源和哈希，避免“凭截图记路线”。
3. 读 `routes`、`waves`、`predefines` 和地图尺寸；不要只读一张 wiki 图。

### 3.2 坐标转换

MAA 使用左上原点的 `[列, 行]`；关卡原始 `routes` 坐标自底向上，必须转换：

```
MAA 行 = 地图高度 - 1 - 原始行
```

- OF-2 地图 7 行，转换是 `[col, 6-row]`。
- OF-8 地图 12×8，转换是 `[col, 7-row]`。

地图高度从关卡数据核实，不要套用别的图。转换后的坐标才是作业里的 `location`。

### 3.3 读时序的三个层次

- `fragment preDelay`：波次片段开始前的等待。
- `action preDelay`：单个出怪动作前的等待。
- `route` 里的 `WAIT`：敌人出生后原地等待，再沿 checkpoints 移动。

这三层不能简单相加当成“接敌秒数”。计划阶段只用来判断先后和大致窗口，真正的接敌时刻以客户端逻辑帧为准。OF-2 的开局猎犬分别在 `[8,3]` 等 50 秒、`[5,3]` 等 25 秒；把水獭部署在等待窗口之后，就会错过第一只猎犬（历史作业已出现该问题）。

### 3.4 从路线推导站位

按这个顺序做：

1. 画出每条 route 的出生点、等待点、汇流点和蓝门。
2. 找汇流点或蓝门前的最后一格：这是守门位，不是“站得近”就行，必须真的挡住路线。
3. 确定被测干员的攻击范围覆盖哪一段；确保敌人会在范围内停留足够久。
4. 检查朝向：守门干员朝来敌方向，治疗/辅助朝向覆盖被测对象。
5. 检查部署费用和顺序：作业按动作顺序执行，费用不够会卡住或延后。
6. 检查技能：状态切换类技能只开一次，不要用“好了就开”。

具体到 OF-2 的路线和站位见 [OF-2 只读采集实机测试站位](of2-test-plan.md)；OF-8 的路线摘要见 [底层能力实测](capability-validation.md)。

## 4. 守门：让实验活到目标事件

漏怪是实验提前结束的最常见原因：敌人进蓝门后战斗结算，采集器还没来得及暂停，目标事件（盾破、召唤攻击、第 N 次治疗）可能根本没发生，或者只拿到半局数据。

守门规则：

1. 每个蓝门至少一名守门干员；有多个汇流方向时按路线分别覆盖。
2. 守门位放在蓝门前的最后一格或汇流点，朝向来敌；不要放在被测干员的输出范围中心，除非确认不会抢目标。
3. 优先用低维护的基石/站场干员：能自回、阻挡稳定、技能只需开一次。山的二技能是状态切换，作业里用 `skill_usage: 2, skill_times: 1`；用 `skill_usage: 1` 会反复切换（历史作业已出现）。
4. 守门干员的输出单独列出或明确排除，不能和被测对象的累计相加后当作实验结论。
5. 一个阻挡干员守不住整局：OF-2 后续波次有绕上路/下路的猎犬、步兵和机动卫兵；按路线增加守门位。
6. 守门干员不能太强到在目标事件前清空所有敌人；需要敌人打到被测对象时，控制守门覆盖范围。
7. 预检：先跑一份只做导航、部署和短等待的作业，确认没有漏怪、没有结算，再跑正式实验。
8. 默认不放怪。若实验本身需要观察漏怪或结算，必须在实验卡里写明，并改用不依赖后续事件的判据。

实测站位例子：

| 关卡 | 被测/观察 | 守门 | 目的 |
| --- | --- | --- | --- |
| OF-2 | 梅尔 `[4,2]` 朝上，水獭 | 山 `[2,3]` 朝右；歌蕾蒂娅 `[2,4]` 朝上 | 守蓝门，防止水獭实验因漏怪提前结束 |
| OF-2 | 闪灵 `[4,4]` 朝上、夜刀 `[4,3]` 朝右 | 山 `[2,3]` 朝右；歌蕾蒂娅 `[2,4]` 朝上 | 隔离数值盾吸收与自然到期 |
| OF-8 | 夜刀 `[3,2]` 朝上，闪灵 `[2,3]` 朝右，煌 `[3,5]` 朝右 | 三人本身分担上路与下方汇流 | 高攻击敌人触发盾破；煌守下方汇流 |

作业文件在 [acceptance/maa](../acceptance/maa/README.md)。原始无守门作业保留为历史执行内容，不能倒改成“有守门的成功实验”。

## 5. 写 Copilot 作业

MAA 的“自动战斗作业”是固定动作序列，不是代理指挥。最小结构：

```json
{
  "stage_name": "OF-2",
  "opers": [
    {"name": "闪灵", "skill": 2},
    {"name": "夜刀"}
  ],
  "actions": [
    {"type": "Deploy", "name": "闪灵", "location": [4, 4], "direction": "Up"},
    {"type": "Deploy", "name": "夜刀", "location": [4, 3], "direction": "Right"},
    {"type": "Output", "post_delay": 8000, "doc": "等第一只猎犬进入夜刀范围"},
    {"type": "Click", "rect": [1208, 52, 1, 1]}
  ],
  "doc": {"title": "ArkDPS 数值盾实验", "details": "不消耗道具；部署完成后暂停"}
}
```

要点：

- `stage_name` 必须与关卡一致；进入关卡详情页后再加载作业。
- `opers` 只列作业会用到的干员；需要指定技能时写 `skill` 索引。练度不够时自动编队会失败或选不到技能，先核对实际练度。
- `actions` 按顺序执行：`Deploy` 部署，`Skill` 点击技能，`SkillUsage` 设置技能策略，`Retreat` 撤退，`Output` 等待并输出文档，`Click` 点击屏幕坐标（本机暂停键约 `[1208,52]`，分辨率变化时先核对）。
- `post_delay` 是 MAA 主机的墙钟毫秒，不是游戏逻辑时间；倍速、加载和调度都会改变对应关系。判定用客户端帧。
- 状态切换技能用 `skill_usage: 2, skill_times: 1`；不要用 `1` 让它反复开关。协议细节见 [MAA 作业协议](https://docs.maa.plus/zh-cn/protocol/copilot-schema.html)。
- 自动生成的召唤物（如医疗探机）可能不接受手动 `Skill` 指令；历史作业曾因此卡住。需要时手动部署，并在记录里标为人工协助。
- 作业文件放入 `acceptance/maa/` 并在该目录 README 登记；作废版本保留但明确标注 `invalid`，不要改写成正确版本。

## 6. 导航与运行

MAA 已封装关卡导航和任务链，不需要反复截图手点。两条路径：

- 内置任务：`StartUp` 启动游戏，`Fight` 选择关卡并作战。
- 自定义导航 + Copilot：用 `baseTask` 组合 `SideStoryStage`、`SlowlySwipeToTheLeft`、`BattleStartPre` 等任务，确认停在关卡详情页，再加载 Copilot 作业。OF-2 的链条见 [of2-navigation-tasks.json](../acceptance/maa/of2-navigation-tasks.json)。

运行前检查：

1. 已在关卡详情页（`BattleStartPre`），不是地图节点、未展开的关卡页或结算页。
2. **代理指挥已关闭**。开启时 Copilot 会在 `BattleStartAll` 触发“接管作战”对话框并停住。
3. 自动编队只在需要时启用，并选择一个可覆盖的编队槽；确认干员和技能真的被识别。
4. 不启用理智药、源石、助战，除非实验明确需要；用到时记录。
5. 事件探针/采集器在点开始行动前就绪；只跑作业不会自动产生 ArkDPS 的事件证据。

MaaCore 的最小驱动顺序（研究脚本，不是产品代码）：

```python
lib.AsstLoadResource(root.encode())          # root 是包含 resource 的目录
lib.AsstSetUserDir(userdir.encode())
handle = lib.AsstCreateEx(callback, None)     # WINFUNCTYPE，保持 callback 引用
lib.AsstConnect(handle, adb.encode(), b"127.0.0.1:16384", b"General")
lib.AsstAppendTask(handle, b"Copilot", json.dumps({
    "filename": path, "formation": True, "stage_name": "OF-2",
    "add_trust": False}).encode())
lib.AsstStart(handle)
# 轮询 AsstRunning；不要用任务完成消息替代战斗帧
lib.AsstStop(handle); lib.AsstDestroy(handle)
```

已实际踩过的坑：

- `AsstLoadResource` 要传包含 `resource` 的根目录，不是 `resource` 自身。
- ctypes 回调必须用 `WINFUNCTYPE` 并保留引用，否则可能崩溃。
- `AsstBackToHome` 在本机回到安卓桌面，不是游戏主页；需要回游戏主页时用 `StartUp`。
- `SingleStep` 的多动作接口不遵循这里使用的 `post_delay` 等待方式；研究控制器要显式等待。
- 导航失败（停在结算页或未展开的关卡页）不是战斗样本；修正导航后重跑，失败回调保留。

## 7. 采样、暂停与判定

1. 进入战斗前挂好事件探针；内存采集器可以先启动并等待战局。
2. 部署完成后用作业里的 `Click` 暂停，或等待到目标帧后暂停；确认游戏真的暂停。
3. 读取带帧校验的累计快照；必要时卸载探针。
4. 记录帧号、游戏逻辑时间、事件条数、客户端累计和归并口径。
5. 失败或提前结束的局单独记录，不并入验收样本。

有效证据至少包括：关卡数据和哈希、作业文件、MAA 回调日志、暂停帧、被测累计、事件合计、守门排除说明。只给“任务成功”不算实验成功。

## 8. 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `BattleStartAll` 失败 | 返回地图后没有重新选中关卡详情 | 重新进入关卡详情页再加载作业 |
| 出现“接管作战”对话框 | 代理指挥仍开启 | 在关卡详情页关闭代理指挥 |
| `Skill 2 not found in quick detection` | 干员练度或技能索引不符 | 核对实际练度；不要先归因于 MAA |
| 山反复切换技能 | `skill_usage: 1` 用于状态切换技能 | 改为 `2` + `skill_times: 1` |
| 无人机作业卡住 | 自动召唤物不接受手动技能指令 | 移除该 `Skill`，人工部署并记录 |
| 等待时间对不上 | 把 `post_delay` 当游戏时间 | 用客户端逻辑帧核对 |
| 实验提前结束 | 漏怪进蓝门 | 按路线加守门位，先跑预检 |
| 导航停在结算页 | 关卡页未展开或任务链错误 | 先识别 `BattleStartPre`，再选地图节点 |
| 第一只怪没接到 | 部署晚于路线等待窗口 | 在 25/50 秒窗口前部署，或换接敌点 |
| `AsstLoadResource` 返回假 | 传了 `resource` 而不是根目录 | 传包含 `resource` 的根目录 |
| 进程崩溃 | ctypes 回调被回收 | 使用 `WINFUNCTYPE` 并保留引用 |

## 9. 边界

- 本手册是研究方法，不是产品采集器的功能说明；事件探针和 MAA 控制器尚未集成正式程序。
- MAA 作业只保证固定动作顺序，不保证每台机器在同一帧暂停；帧号、墙钟和游戏时间不能互相替代。
- 公开关卡数据是社区提取，可能落后于游戏版本；实机不一致时以实机为准。
- 守门干员的练度、技能和阵容会改变接敌时序；换了配置就重新预检，不要复用旧结论。
- 本手册不覆盖所有召唤体系、特殊护盾、游戏/模拟器重启后的恢复。
