# 手动对局性能计时

在「设置 → 诊断工具」开启「性能计时（低开销）」。默认关闭，可独立于详细调试日志使用。

## 异步采集候选的计时口径

本文后续关于同步回调、VM 等待与锁内耗时的表格属于旧计时包，不能用于解释异步候选的
游戏回调。新调用链见[原生现场采集与单消费者](native-capture-worker.md)。业务事实及统计
口径保持共用；游戏现场与后台归约的执行位置已经改变。

异步候选另行记录 `async_capture`：raw reserved/processed/closed/published 水位、各线程
出生身份和 lane 世代、入队记录与字节、峰值占用、捕获到重放年龄及明确缺口。
`callback_timing` 按 lane/hook/进入或退出随机约1/128抽样，保存现场读取次数、字节和
捕获/入队墙钟。抽样从启用判断之后开始，包含已注册线程的身份验证、参数读取、现场捕获
及发布，不含第一次注册、采样决策、指标记账或中间的原函数执行。
开启计时时，队列年龄的捕获时间戳仍按每条事实记录，不能把它说成只有抽样时才读取时钟。

性能开关关闭时不新增 QPC 读取或逐回调日志。开启后仅通过已有宿主回复按秒写出有界
汇总；真实计时样本为0、计数快照不一致或字段缺失时保留未知，不补零。
各阶段均值必须与样本数和覆盖边界一起解释，不能将抽样总和乘128当成精确CPU占用。
新候选是否改善游戏 FPS 仍需同级实机复测；离线队列和自有进程吞吐测试单独登记。

| 层 | 阶段 | 计量方式 |
|---|---|---|
| ArkPie 原生钩子 | 每个钩子的 enter/leave；VM 获取等待、持有、JS 回调 | 调用数全量；时间随机约 1/128 抽样，嵌套采样继承 |
| ArkPie 宿主请求 | mark/read/ack 的 VM 等待、持有、JS 分派 | 请求阶段全量计时；读取细节约 1/128 请求抽样 |
| 原生读取 | ReadProcessMemory 调用、请求字节、耗时 | 只在读取明细抽样范围内计量，含失败尝试 |
| 原生传输 | JSON 解析、外层编码、管道写出 | 全量请求阶段；不包含等待下一条命令的空闲时间 |
| Python 采集 | 快照读取、名单读取、事件获取、消费、统计结果生成、归档 | 每批计时；包含时间与自身时间分别记录 |
| Python 展示 | 行投影、面板生成、完整快照、stdio 各阶段 | 每批/每次发布，按秒汇总 |
| WPF | 管道写入、等待回复、校验、ApplyState、Measure、Arrange | 每次发布/布局，按秒后台汇总 |

Python 与 WPF 部分适用于模拟器和 PC。原生钩子、QuickJS 锁及原生传输字段仅由 ArkPie DLL 提供；其他后端没有这些字段，不能把缺失当成零。WPF 布局时间不代表 GPU 绘制或真实呈现帧时间。

## 低开销边界

- 关闭时原生回调只做启用判断，不读时钟、不更新性能计数、不分配内存、不输出日志；Python/WPF 新增的时钟调用同样关闭。
- 原生启用时使用固定 16 个线程槽，每个线程只写自己的计数；没有性能计数全局互斥锁。线程槽不回收，耗尽时明确报告 `thread_overflow`。
- 回调的计数和随机抽样不写文件、不发送 IPC。原生汇总挂在已有 mark 回复上，最多每秒一次；快照最多 128 行，只做有界重试，输出在释放 VM 锁后生成。
- 宿主普通日志只接收清洗后的有界数字汇总；详细原始事件日志无需开启。采集日志延后至原生采样重试突发结束后写出，队列最多 8 条，溢出用 `queue_dropped` 报告。
- WPF 同时最多一个后台写任务；磁盘慢时保留聚合数字，不累计写任务。停止前不足一秒的尾窗可能没有输出。

## 日志及解释

便携包的 `collector/runtime`（或自定义 state-dir）下：

- `captures/wpf-*.jsonl`：`performance_timing`、`native_performance_timing`。
- `wpf-collector-*.log`：Python 展示/stdio 汇总，前缀 `[performance_timing]`。
- `wpf-performance.jsonl`：WPF 阶段汇总。
- 原有游戏 FPS 日志照常记录，用 UTC 时间对齐；原生 QPC 和宿主单调时钟用于精确阶段耗时。

原生数字是同一个 PID/创建时间内的累计值。相邻汇总作差才能得到窗口内的 calls/samples/ticks；计数峰值是该运行时累计峰值。单位转换：`ticks * 1000 / qpc_frequency` 为毫秒。传输写出完成时间在下一份快照中可见。

`samples=0` 代表尚无时间样本；`read_detail_spans=0` 代表没有读取明细样本，不能证明没有读取。`read_calls/read_bytes/read_ticks` 仅属于明细抽样范围，不是全局读取总量。线程槽耗尽、`omitted_cells`、`skipped_busy_cells` 非零时覆盖不完整。不要将随机样本的最大值写成总体 p99，也不要把抽样耗时乘 128 当成精确总耗时。

VM 等待是获取锁的墙钟时间，包含可能的调度挂起。VM 持有、JS 与读取时间是包含关系，不能直接相加；Python 的 exclusive_ns 用于避免嵌套重复计数。原生 enter/leave 不包含中间原始游戏函数的执行时间。严谨区分锁争用与调度停顿仍需结合系统线程采样。
