# 事件队列内存预算与采样重试

本轮基于已发布 rc.47 的 main `fd928d06`。队列预算解决突发缓冲容量，窗口重试修复健康观察器被错误关闭；两者分别验收。容量增加不代表消费吞吐或游戏 FPS 已改善。

## 配置与实际生效

`ConnectionConfig.event_queue_memory_mib` 唯一保存用户偏好，范围为整数 512–2048 MiB，缺项默认 1024 MiB。WPF 独立保存该值，Python 在新游戏进程的原生观察器初始化前传入 `initialize.event_queue_memory_mib`。已初始化的 ArkPie 源不热调整、不停止重装；界面分别显示计划值与原生 readiness 证明的实际值，变更等待下次游戏启动。

启动参数 `--event-queue-memory-mib` 可覆盖本次运行的计划值；用户主动保存新预算后，仅清除此字段的启动覆盖。其它连接参数不受影响。未报告预算能力的旧组件或其他后端，其实际预算保持未知或不适用。

此值限定**一个游戏进程中全部原生事件队列**的槽位、数据缓冲及队列控制存储总量，不是每个线程各自的容量，也不是进程 RSS 上限。槽位与字节容量分别受限，页对齐和完整缓冲块会留下少量不能使用的预算。

## 内存所有权

- `CaptureLanes` 计算统一布局并保留线程队列；`CaptureSpillPool` 管理固定描述符、预备共享块与归还；`CaptureQueue` 唯一拥有每块槽位和数据环。
- 私有队列仍是 16 组 2048 槽位与 2 MiB 数据区。共享块按 65536 槽位与 16 MiB 数据区配套准备，槽位实际大小纳入预算。
- 后台启动时只准备少量共享块，低水位时继续准备。准备包含分配、提交和逐页触页，完成后才发布可借用状态。游戏回调只访问已准备的内存，不申请、扩容、触页初始化或等待消费者。
- 排空、排除写入者并再次证明为空后，后台可释放超过预备量的共享块；Windows 使用 `VirtualFree(MEM_RELEASE)` 归还提交，不靠 `delete` 或空队列推断已回收。复制出的消费记录由消费者自己的缓冲持有，不依赖已归还的共享块。
- 队列之外，16 个 Lane 的调用栈、现场快照、父检查点与序列化 scratch 这四类工作缓冲约 62 MiB，单列为 `fixed_capture_working_bytes`；Lane 的其它控制字段和对齐仍计入队列预算。消费者缓冲、QuickJS、模块、分配器等也不属于队列预算。因此空闲预备队列约 103 MiB，不等于整个采集组件或游戏的常驻内存只有 103 MiB。未使用 `VirtualLock`，操作系统仍可换页；后台预备避免的是由游戏回调执行显式分配、提交和首次触页初始化。

动态准备跟不上或真实容量不足时仍明确产生缺口；生产者不能在热路径分配救场，也不能覆盖未消费记录。队列满可附首例槽位、字节、未准备块与占用快照，固定容量、仅在失败分支采集，经已认证错误回复交给日志；它不授予发布、完整性或 ACK 权限。并发故障时若首例快照尚未发布，该次回复保持未知，不为诊断等待游戏线程或推迟缺口生效；全局首因不是队列满时不附队列满归因。

## 窗口准入与观察器寿命

2026-11-27 22:59:28 的 rc.47 第三回合记录，最后已观测原始水位为 reserved/processed/closed/published=25972，failure=0，队列峰值仅 236 条、856820 字节。随后 `AutoChess counter clock is outside the event window` 被升级为 `StreamGap`，关闭健康源后同进程只能得到 `native_not_ready`。

证据是 `runtime/queue-budget-recovery/incident-evidence.json` 登记的原文件前 624 行；1744046 字节，SHA256 `3b667fd7850a80aef3318da852de89c2b7af0b0a636838047cc17b6191e1379d`。这不证明故障瞬间每个时钟子条件；原日志没有逐次 before/anchor/after 值。

当前窗口的 `BarrierBusy` 必须保持可重试类型，经既有 `CaptureRetry` 节奏返回，不读取或确认事件，不归档/推进当前事务，也不关闭健康观察器。合法窗口到来后重新验证原始范围。来源、进程、构建、记录、作用域和序号的真实缺失或冲突仍拒收为缺口；不能把任意 `StreamGap` 变成无限重试。历史辅助证据不足仍按其原有归档完整性合同处理。

失败上下文只记录本次已有的时钟、作用域和游标值及调用阶段，固定字段、固定长度，不增加游戏现场读取。业务解释、统计归属及 ACK 仍由现有共享入口与生命周期所有者负责。

## 变更控制与验收边界

本轮扩展现有配置、原生队列和 typed retry，没有新增伤害账本、作用域真值或治理机制。重要拒收条件保持严格：预算/几何错误在初始化边界失败，队列失败在原生入队边界失败，窗口临时错位在当前采样事务提交前重试。

验收分别覆盖配置往返与待生效状态、512/1024/2048 布局、槽位及字节边界、后台增长与回收、突发/追平、真实缺口和 read/ACK，以及窗口重试到 worker 的恢复与真实故障负例。最终结果登记在本轮 `runtime/queue-budget-recovery/` 回执；未运行的压力或实机条件不能标为通过。
