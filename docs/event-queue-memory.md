# 事件队列内存预算与采样重试

本轮基于已发布 rc.47 的 main `fd928d06`。队列预算解决突发缓冲容量，窗口重试修复健康观察器被错误关闭；两者分别验收。容量增加不代表消费吞吐或游戏 FPS 已改善。

## 配置与实际生效

`ConnectionConfig.event_queue_memory_mib` 唯一保存用户偏好，范围为整数 512–2048 MiB，缺项默认 1024 MiB。WPF 独立保存该值，Python 在新游戏进程的原生观察器初始化前传入 `initialize.event_queue_memory_mib`。已初始化的 ArkPie 源不热调整、不停止重装；界面分别显示计划值与原生 readiness 证明的实际值，变更等待下次游戏启动。

启动参数 `--event-queue-memory-mib` 可覆盖本次运行的计划值；用户主动保存新预算后，仅清除此字段的启动覆盖。其它连接参数不受影响。未报告预算能力的旧组件或其他后端，其实际预算保持未知或不适用。

此值限定**一个游戏进程中全部原生事件队列**的槽位、数据缓冲及队列控制存储总量，不是每个线程各自的容量，也不是进程 RSS 上限。槽位与字节容量分别受限，页对齐和完整缓冲块会留下少量不能使用的预算。

## 内存所有权

- `CaptureLanes` 计算统一布局并保留线程队列；`CaptureSpillPool` 管理固定描述符、预备共享块与归还；`CaptureQueue` 唯一拥有每块槽位和数据环。
- 私有队列仍是 16 组 2048 槽位与 2 MiB 数据区。共享块按 65536 槽位与 16 MiB 数据区配套准备，槽位实际大小纳入预算。
- 后台启动时只准备少量共享块，低水位时继续准备。准备包含分配、提交和逐页触页，完成后才发布可借用状态。游戏回调只访问已准备的内存，不申请、扩容、触页初始化或等待消费者。
- 排空、排除写入者并再次证明为空后，后台可释放超过预备量的共享块；Windows 使用 `VirtualFree(MEM_RELEASE)` 归还提交，不靠 `delete` 或空队列推断已回收。复制出的消费记录由消费者自己的缓冲持有，不依赖已归还的共享块。
- 队列之外，16 个 Lane 的调用栈、现场快照、父检查点与序列化 scratch 这四类工作缓冲约 62 MiB，单列为 `fixed_capture_working_bytes`；Lane 的其它控制字段和对齐仍计入队列预算。消费者缓冲、QuickJS、模块、分配器等也不属于队列预算。因此空闲预备队列约 103 MiB，不等于整个采集组件或游戏的常驻内存只有 103 MiB。未使用 `VirtualLock`，操作系统仍可换页；后台预备避免的是由游戏回调执行显式分配、提交和首次触页初始化。

动态准备跟不上或真实容量不足时仍明确产生缺口；生产者不能在热路径分配救场，也不能覆盖未消费记录。队列满可附首例槽位、字节、未准备块与占用快照，固定容量、仅在失败分支采集，经已认证错误回复交给日志；它不授予发布、完整性或 ACK 权限。并发故障时若首例快照尚未发布，该次回复保持未知，不为诊断等待游戏线程或推迟缺口生效；全局首因不是队列满时不附队列满归因。

## 变更控制与验收边界

本轮扩展现有配置、原生队列和 typed retry，没有新增伤害账本、作用域真值或治理机制。重要拒收条件保持严格：预算/几何错误在初始化边界失败，队列失败在原生入队边界失败，窗口临时错位在当前采样事务提交前重试。

验收分别覆盖配置往返与待生效状态、512/1024/2048 布局、槽位及字节边界、后台增长与回收、突发/追平、真实缺口和 read/ACK，以及窗口重试到 worker 的恢复与真实故障负例。最终结果登记在本轮 `runtime/queue-budget-recovery/` 回执；未运行的压力或实机条件不能标为通过。

## 2c40e4a 后续复现与拒收事务

2026-11-27 23:52:09 再次掉观察器的冻结证据位于 `runtime/observer-drop-2c40e4a-20261127/`：原日志前689行、880611字节，SHA256 `b5707610f6518088d5a830c1c70dcd34d4209b30aa31c567398e256ece841bc3`。最后原始水位6638全部处理、闭合和发布，277份原生摘要均为 failure=0，队列仅使用预备块。故障前的窗口忙重试已经成功恢复交付；此次另一个 `StreamGap` 随后触发通用会话清理，关闭不可重装的原生源。普通日志未保留最初异常的具体分支，不能据此将现场初因断定为下面的某个合成反例。

新增的自有反例验证了两处生命周期缺口：已验证的 pending 小局事务建立了 generation，但后续覆盖拒收使 capture 关闭；宿主 pending 若未退休，下次会重复初始化同一 generation。另一处是宿主校验拒收穿过 worker 通用异常出口，即使运输仍正常，也会导致一次性输入被关闭。

本轮分别约束这两处所有权：

- 只有独立 start 已验证、属于当前 generation 且 capture 已 closed/gap 的终端拒收，才能退休宿主 pending。尚未验证、字节预算不足或窗口忙的 pending 保留原事务、分页与游标。
- 退休只结束宿主交接，不确认源事件。当前 capture 保留同来源、同 cursor lifetime 的拒收范围；新小局基线或采样切片不能把未接纳的旧尾部当作已消费，也不能据此声明完整覆盖。
- 宿主 `StreamGap` 保持事件拒收。仅当已核验的同 PID/出生源仍为 READY、管道未 poison、句柄仍开放且进程仍在运行时，worker 才保留同一 session/source 所有权，按原采样节奏继续。它不转换成 `CaptureRetry`，不获得短重试特权，也不授予 ACK。
- 原生 FAILED、真实管道错误、结构或容量故障、进程变化及未知健康状态保留原故障路径。运输正常并不证明某笔数据可信。

`capture_error.stream_gap_failure` 在普通与调试日志中使用同一有限清洗：原因码、acquire/prepare_observer/consume/acknowledge阶段及最多8个白名单模块/函数/行号。没有匹配的错误保留为 unclassified；不记录任意异常文本、路径、locals、账号或令牌。原生队列实现、内存预算和源事实不因这些宿主修复而改变。

新增诊断与终端拒收范围分别归属原错误出口和当前 capture，不建立另一套统计、源游标或 ACK 所有者。专项负例保护 pending 保留/退休、旧尾部不 ACK、健康源不被误关及真实错误继续失败；最终结果以本次候选自身的回执为准，先前6671项通过不代表后续实机已稳定。

事件标记和独立采样器各自有真实观察时间。已接纳的原生世代绑定由 `NativePcBinding` 拥有，记录进程出生、构建、根、关卡及独立采样串号；同局历史标记不能因晚于它的采样时钟而预测一个新串号。首次候选只作窗口验证的提议，在既有独立样本接纳回执处提交；被真实采样重置证伪的未提交候选可以退休重采，已经确认的映射不能重写。原有窗口、跨局、来源和ACK验证继续生效。

空作用域交接只负责建立新采集段的真实基线。若该基线已经由 `_events` 接纳，而紧接着的当前样本更新暂时失败，原生尾部仍属于同一开放 capture 的后续输入。此时依据同一观察器与游标寿命、同一锚点和准确基线证明退休宿主 pending；不再重复初始化已建立的世代，也不确认未消费尾部。基线尚未接纳、换源、游标变更及真实拒收继续保留原严格路径。

两条错误路径已用实际产品方法和自有对象复现；普通实机日志未保留每次标记和最初短重试的全部值，不能断言它们解释了现场的每一次拒收。离线回归与新包实机恢复效果分别验收，不以处理速率或回归通过宣称游戏FPS改善。
