# 重连后的历史数据：已知证据与未决能力

**当前产品决定（2026-11-07）：取消独立重连恢复需求。** 中途启动读取本局已有伤害/治疗累计，速率从采集开始计算；启动前护盾累计无法补读是已接受限制，不阻塞开发。设备常驻观察器不是 V1 前置要求。见 [开发备忘](development-notes.md)和 [V1 设计基线](v1-design.md)。下文保留先前调查及决策演进，其中“完整累计恢复须验收”的旧门槛已被取代。

2026-11-07。早期为只读快照调查；后续在用户授权的 MAA 自动战斗中加入原生方法事件观察，没有启用游戏的额外详细日志或修改战斗数值。

## 结论

已验证可重新读取本局累计伤害与治疗；实时观察可以取得原生事件的游戏逻辑帧，仍未验证能恢复观察开始之前每次输出的发生时间。客户端执行战斗，即使只在结算时通信，也不必保留每一步的全部结果；网络通信时机本次未核实。累计状态、可重放的输入记录和直接可读的事件历史是三种不同能力。

2026-11-07 用户决定：如果没有可用逐事件历史，V1 不做完全重连恢复，只要求恢复完整累计。结合当前版本已核查来源均未提供可用时间线，V1 采用该范围，不再以整局事件回补作为发布前置条件。这是基于已验证版本的产品取舍，不是所有游戏模式均无历史记录的断言。伤害、治疗累计恢复已验证；有效护盾的完整累计恢复仍需单独验收。

## 之前五笔命中的时间来自哪里

acceptance/verify_evidence.py 对相邻采样的夜刀累计伤害做差；原有 hits.frame/game_time 记录后一次采样的游戏帧/时间，不是已解析的游戏原始命中时间。现补充 observation_interval 与 timestamp_basis，避免把观察时间误读为精确命中时间。

| 累计增量 | 前后采样帧 | 可定位的游戏时间区间（左开右闭） |
| --- | --- | --- |
| 280 | 630 → 636 | (20.99998, 21.19998] |
| 280 | 666 → 669 | (22.19998, 22.29998] |
| 200 | 887 → 890 | (29.56664, 29.66664] |
| 200 | 919 → 921 | (30.63330, 30.69997] |
| 200 | 952 → 955 | (31.73330, 31.83330] |

这是单个夜刀输出、NPC 累计不变的隔离验证。若相邻采样间发生多次命中，累计差值只提供总和，不能拆开次数、先后与精确时间。game_time/frame 是采样时读到的游戏时钟；observed_at 和 captured_monotonic 是采集主机时间。原始记录未丢失采样时间，缺少的是游戏原始逐击时间线。

连续采样能够形成可回看的累计曲线与区间增量，用于估算近期 DPS；重连时只有单个累计快照则不能补出断连期间的分布。不能将该限制扩大为“连续快照无法用于任何复盘”，也不能将隔离对账扩大为普遍逐击捕获能力。

## 类型证据详情

来源：[上游固定版本 PC 类型转储](https://github.com/Tim23333/Arknights_timer/blob/5734c30bf54780056ff758505380322c0cf519fe/game_data/reference/pc_x64/dump.cs)。PC 类型用于研究语义，不能直接作为 Android 内存布局。

- CharAdvancedStats.snapshots 是 List<CharacterSnapshot>（397984–397993）。CharacterSnapshot 属于 AntiCheat，记录时间戳、属性、天赋、技能与特性（541909–541936）；MAX_SNAPSHOTS_FOR_SINGLE_CHARACTER 为 1（398172）。这条快照不是逐次输出历史。
- BattleLogger.Journal 包含 metadata、squad、操作 logs、randomSeed、runeList（397914–397921）。这些是重放输入的线索，不等于无需重新模拟便可读取完整伤害时间线。
- BattleVerboseRecorder 的 LogItem 包含 frameCnt、source、target、modifier，modifier 含 realDelta、afterValue；类型包括 MODIFY_HP、MODIFY_EP，存在 m_detailLogs（398388–398484）。这条结构有恢复逐事件历史的可能，但类型存在不能证明正常游戏启用了它。

## 当前 Android 实机观察

Android 2.7.91 字段转储明确 BattleLogger.m_verboseRecorder 位于 Logger+0x38。本次使用独立只读连接，未干扰主统计窗；当前演习 frame 24，游戏时间约 0.80 秒，m_verboseRecorder 为 0x0。读取前后战局、帧一致，设备侧帧校验通过。完整观察见 ../acceptance/verbose-pointer-observation.json。

因此此局此刻没有实例化这条记录器。此结果不能推广为所有模式、战斗阶段或其他尚未发现路径都没有历史记录；也不足以承诺本产品可补齐全部事件。

## History source audit 线索核对

子智能体的[原始调查](../acceptance/history-source-audit.json)确实给出了进一步检查路径，而没有宣布发现了可用的逐事件历史。后续核对结果如下：

| 线索 | 后续证据 | 对恢复能力的判断 |
| --- | --- | --- |
| BattleVerboseRecorder / FileLogger / BattleLog | 多阶段 m_verboseRecorder 为空；BattleLog 目录为空，待上传文件 0 字节 | 当前普通关卡没有取得详细事件日志 |
| ExtraBattleInfo 的时间、帧号、ModifierRealDelta 节点 | Android 字段核实后，在第 2728、3040 帧读取：extraInfo 为空，extraBattleInfo 和 clientAntiCheatLog 无条目，扩展统计只有击杀计数 | 节点具备记录能力不等于本局启用了完整记录 |
| ReplayController / Journal | 实机操作日志为部署等玩家输入，没有随普攻增加 | 不能直接读取伤害/治疗时间线；重新模拟整局不纳入此次恢复功能 |
| CharacterSnapshot / EnemySnapshot | 类型审计确认属于属性快照，声明的单键快照上限为 1 | 不构成逐击历史 |

特殊模式、多人日志和未识别的其他结构没有被穷尽；不为排除这些理论可能性继续阻塞 V1。上述证据已足以确定本版没有可依赖的通用逐事件恢复来源。

## 先前的 V1 重连范围（已由中途启动需求取代）

后续 OF-2 / OF-8 已实测停采期间累计补读；检查了 BattleStats 的 34 个实例字段、扩展字典、操作日志和 BattleLog 文件，仍未取得完整旧事件序列。实时事件和最终累计已可对账，详细证据见 [能力报告](capability-validation.md)。这支持进一步设计开局持续记录，不支持宣称中途首次连接可无条件补回全部历史。

重连恢复本局累计，以包含缺口期间输出的可靠总数替换旧基线，不能重复相加。总伤害、总治疗及其分类/召唤归属仍按既定口径验收。有效护盾没有已验证的游戏原生吸收累计，不能用剩余盾量补回；完整盾累计的保存与恢复路径仍是独立能力缺口。

补充实验已验证：设备端观察器从开局持续运行、主机退出并移除 Frida 转发后，能够从设备日志恢复断连期间的有效护盾累计；观察器也停止时的原生补回仍未建立。详见 [恢复实验及限制](recovery-validation.md)。该研究证据不等于设备观察器的正式产品实现已获验收。

不要求回填未记录的逐次事件、最近 5 秒分布或整局接敌区间。近 5 秒指标从重连后的可靠连续观察重新起算，未满窗口按已观察游戏时间作分母；重连读到的全局累计只作基线。保留已可靠记录的时间线与最近 100 局战绩，不将缺口写成零。接敌指标不得以恢复的全局累计除以部分已知活跃时间；缺口情况下的具体展示仍需在界面设计中明确，不能冒充完整本局指标。

只有未来获得新的实际事件历史证据，才另行评估扩大恢复范围；不将启用记录器、重新模拟战斗或恢复所有特殊模式日志列为本版必做调查。

## 1.5 秒指标的事实更正

本地固定版本 characters.json 的 baseAttackTime：空爆、陨星为 2.8 秒，Lancet-2 为 2.85 秒；[空爆资料](https://wiki.biligame.com/arknights/%E7%A9%BA%E7%88%86)也标注 2.8 秒。1.5 秒作为用户选择的统一活跃阈值保留，但不是基础攻击间隔的上限。慢攻持续输出可能被分割为多个活跃区间，因此结果可能高于按连续交战时间计算的平均值。
